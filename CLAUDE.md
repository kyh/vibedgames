# Agent Instructions

## Agent-driven development

[`AGENTS.md`](./AGENTS.md) is the runnable guide — quickstart, env files, seeded logins, headless auth, the `pnpm verify` gate, an agent-browser recipe, and which surfaces are checkable at runtime versus which need a human. Reach for it when you need to run, sign in, or verify something; a small edit does not need it. This file carries the product context, architectural decisions and conventions that sit on top of it.

- **`pnpm lint` is a clean gate.** `oxlint.config.ts` extends the ultracite presets (core, react, anti-slop); every rule is an error. Fix the code, don't add config overrides; a `// oxlint-disable-next-line rule -- why` needs a stated reason.

## What This Is

**vibedgames** — infrastructure platform for deploying, hosting, and adding multiplayer to browser games. Users build games locally, deploy via CLI (`vg deploy`), and their game is served at `{slug}.vibedgames.com`. The web app is the central hub for discovering and playing games.

**The primary user of the `vg` CLI is a coding agent, not a human.** A human prompts their agent ("build me a bomberman game"), and the agent uses `vg` + the bundled skills to scaffold, generate assets, add multiplayer, and deploy. Optimise CLI UX accordingly: machine-readable output (`--json`), self-describing errors, deterministic exit codes, skills that document the exact commands the agent should run. Friction that a human would tolerate ("now open this URL...") blocks an agent.

## Product & Business Context

- **The bet (why us):** _Seed your coding agent with the abilities of a full game studio._ The wedge isn't "another hosting platform" — it's that an agent, armed with `vg` + the bundled skills, can do everything a studio does (scaffold, generate art/audio, add multiplayer, ship) without the human assembling an engine, art pipeline, or server stack. The differentiator is being _agent-native and end-to-end_.

## Key Architectural Decisions

- **Games are untrusted user code.** Session cookies are scoped to apex domain only (`vibedgames.com`). Games on `{slug}.vibedgames.com` subdomains cannot access auth cookies. CSP `frame-ancestors` restricts embedding. Never weaken these boundaries.
- **Single active deployment per game.** No version history, no rollback. New deploy replaces old. R2 keys are `games/{gameId}/{deploymentId}/{path}` — immutable per deployment, enabling long cache (1yr) for assets and short cache (60s) for index.html.
- **`vg login` is OAuth device authorization (RFC 8628).** The CLI is the first-party public client `vibedgames-cli` (`CLI_OAUTH_CLIENT_ID`/`CLI_OAUTH_SCOPES` in `@repo/contract/cli`), seeded at auth init with only the device-code and refresh-token grants, every scope and the `/api` resource. `oauthDeviceAuthorization()` (`device_code` table) issues the code; the person approves it at `/device`, which claims the code for the signed-in person and shows the client and scopes before Approve/Deny. The CLI saves an hour-long access token with its refresh token and expiry in `~/.config/vg/auth.json` and refreshes before a request that would find it expired (`apps/cli/src/lib/oauth.ts`); refresh tokens rotate, and `refreshTokenReuseInterval` replays a just-rotated response so parallel `vg` commands do not trip reuse detection, which revokes the family. `vg logout` revokes the refresh token. The CLI shows in Settings → Connected apps by its live refresh token (a device grant records no consent). The pre-OAuth login (`auth.cliInit`/`cliPoll`/`cliConfirm`, `/auth/cli`) is gone: a `vg` from before it must update to log in, though a login it already saved works until that session ends.
- **better-auth 1.7 scopes account identity by `(issuer, accountId)`.** `account.issuer` is NOT NULL with a unique `(issuer, accountId)` index (`account_issuer_account_id_uidx` in `packages/db/src/drizzle-schema-auth.ts`). Credential accounts carry `local:credential` with `accountId` = the owning user's id; an OAuth provider with no real issuer carries `local:oauth:<providerId>`. Keep `better-auth`, `@better-auth/api-key` and `@better-auth/expo` on the same minor. Nothing in `pnpm verify` touches D1, so a schema/column mismatch surfaces only as a failed sign-in against the live database — any further change to these tables needs a matching `db:push` plus a backfill of existing rows.
- **Never regenerate the auth schema with `@better-auth/cli`.** It is stuck at 1.4.21: `generate:auth-schema` emits no `issuer`, and it strips the hand-curated `index(...)` calls and the hand-added `rate_limit` table. Edit `drizzle-schema-auth.ts` by hand.
- **Declare uniques as named unique indexes, never `.unique()`, and keep the composite PK named `deployment_file_pk`.** Production D1 was pushed by drizzle-kit 0.31, which spelled every `.unique()` as a `CREATE UNIQUE INDEX <table>_<column>_unique` and left the `deployment_file` PK unnamed (introspected as `deployment_file_pk`). drizzle-kit 1.0 spells `.unique()` as an inline `UNIQUE` constraint and names PKs, and treats either difference as a table recreate: `PRAGMA foreign_keys=OFF; CREATE __new; INSERT; DROP; RENAME`. D1 ignores that PRAGMA, so the `DROP` cascades through every `ON DELETE CASCADE` child (`account`, `session`, `game`, ...). With `uniqueIndex("<table>_<column>_unique")` in the table's extra config and that PK name, `drizzle-kit push --explain` against a 0.31-shaped database reports no changes. `drizzle-kit push` applies a recreate without asking, so `db:push-remote` prints the `--explain` plan first and applies only on a typed `y` — refuse a plan that recreates a table.
- **Every PR gets Cloudflare Worker Previews, Vercel-style, driven by Actions rather than Workers Builds.** `.github/workflows/preview.yml` runs on `workflow_run` after CI is green (same-repo branches only, since that trigger holds secrets), deploys `cf previews deploy pr-<n>` for web and party when the PR touches them, keeps one sticky status comment plus a GitHub deployment per Worker (`.github/scripts/worker-preview.mjs`), and deletes the previews when the PR closes. Previews inherit no bindings: each `cloudflare.config.ts` binds, when `isPreview`, `vibedgames-preview` (D1) and `vibedgames-games-preview` (R2) by name, which the workflow creates on first use. PR code never reaches prod D1 or the prod bucket. The games Worker has no preview because it routes by `{slug}.vibedgames.com`. Preview secrets live in Cloudflare's preview base config (`wrangler preview base-config secret put --worker-name <worker>`; `cf` has no preview secret command yet), not in GitHub.
- **Multiplayer is host-authoritative, last-write-wins.** No conflict resolution. First player becomes host; if host leaves, reassigns. Good for turn-based and host-controlled games. Real-time feel comes from the SDK's netcode helpers, never a hand-rolled throttle or lerp. `FixedRate` drives send clocks. `Interpolator` renders remotes from sender-stamped updates. A guest's own body is predicted locally and corrected by `Reconciler`. Intents go to the host only, and the host handles its own locally. The party server relays a host's `state_patch` (path ops: the leaves that changed) to everyone but the host. Beyond relaying, the server runs only game-agnostic room services: server time (`serverNow()`, the timebase every stamp uses), first-come claims, ordered input ticks for lockstep/rollback, radius interest filtering, player-state limits, persistence of shared state and claims, host-set room locks and meta, and lobbies (`VgLobby`) that list the rooms naming them and quick-match players into the fullest open one. No back-compat in this protocol: SDK and server ship together, and a game that changes its own wire format versions its room ids.
- **Plugins ship from a mirror repo.** `kyh/vibedgames-plugins` holds only `plugins/`, `.claude-plugin/` and `LICENSE`, synced by `.github/workflows/sync-plugins.yml` (deploy key in the `PLUGINS_MIRROR_DEPLOY_KEY` secret). `vg init` and the plugin directory listing point at the mirror because both download a whole repo archive and this one is ~140 MiB compressed. Edit skills here; anything committed straight to the mirror is overwritten on the next sync.
- **`vg` publishes as one esbuild bundle with no dependencies.** `apps/cli/scripts/build.mjs` inlines every dependency (their licences go to `dist/THIRD_PARTY_NOTICES.txt`) and splits each command into a chunk loaded when it runs, so a cold `npx vibedgames` is one small download that no transitive package can print a deprecation warning into. A runtime dependency of the CLI goes in `devDependencies`. Source (`src/lib/`) and chunks (`dist/`) sit at different depths, so a file the package ships is found from `PACKAGE_ROOT` (`src/lib/package-root.ts`), never spelled as `../..`. Every request carries `x-vg-cli: <version>` (`@repo/contract/cli`). Builds before it (≤0.6.3, oRPC 2.0.0-beta.31) refuse an error body without oRPC's old `inferable` field, so `apps/web`'s RPC handler adds it back for Node requests without the header; delete that once those installs are gone.
- **Deploy on push to main.** GitHub Actions detects changed apps and deploys via `cf deploy --prebuilt`. Never run `cf deploy` locally. Changed example games (`games/*`, plus anything downstream of a changed package) deploy the same way through `vg deploy`, authenticated by the `VG_TOKEN` repo secret — an API key from Settings.
- **Signup is open; credit is bought or redeemed.** New accounts start at $0. Credit arrives three ways, all as ledger entries: a Stripe Checkout purchase (`credits.checkout` returns a hosted URL; only the signed `checkout.session.completed`/`async_payment_succeeded` webhook at `/api/stripe/webhook` credits it, keyed `purchase:{checkoutSessionId}`, $1 paid = $1 credit), a credit code redeemed in Settings or with `vg credits redeem` (`code:{codeId}:{userId}`, once per account per code, within the code's `max_uses`), or an admin grant. Credit codes live in the `invite_code` table — it predates launch, when the same codes gated signup, and renaming it would be a recreate. Accounts that signed up with an invite before launch (`user.invited_by_code` set) still get the old $20 `signup:{userId}` grant, lazily on first credit access; nobody else does. Either of `STRIPE_SECRET_KEY` / `STRIPE_WEBHOOK_SECRET` unset turns purchases off, nothing else: `credits.me` reports `purchasesEnabled: false`, Settings shows only the code button, checkout answers 412 and the `insufficient_credits` message offers codes only. Neither is required to deploy: `apps/web/cloudflare.config.ts` leaves them out of production builds, and a key set later with `cf workers secrets update` binds anyway.
- **Per-user generation credits (micro-USD ledger).** `credit_entry` is an append-only ledger of integer micro-USD deltas — balance is `SUM(delta_micro)`, there is no cached balance column, and idempotency lives in deterministic entry ids (`signup:{userId}`, `code:{codeId}:{userId}`, `purchase:{sessionId}`, `hold:{requestId}`, ...). `generation` tracks the per-request lifecycle: `generate.forward` blocks a non-admin's queue submits at balance ≤ 0 (`insufficient_credits`) or to an endpoint `GET /v1/models/pricing` lists no price for (`unknown_endpoint`; an admin's are metered but never blocked), debits an estimated hold at submit (provider historical per-call estimate, clamped $0.01–$5), settles to actual cost from the `x-fal-billable-units` result-fetch header and the endpoint's unit price, and refunds holds when a status poll reports FAILED/CANCELLED. Pricing that cannot answer (network error, 5xx, 429) never blocks a submit: it holds the estimate, else a flat $0.10, and settles at the hold; only a priced answer is cached (`packages/service/src/credits/endpoint-pricing.ts`). The ledger reads a queue hop's endpoint and request id off `path` as sent, while fal percent-decodes the path and finds its application whatever the case, so the contract holds a queue path to lowercase letters, digits and `-._~/`, and every queue POST bills as a submit whatever its path: otherwise the ledger prices or settles a hop other than the one fal runs. Only generation is metered; deploys/hosting are free. Never bypass the gate or write ledger rows outside `packages/service/src/credits/`.
- **Playtest decisions go through TypeSafe Jev (internal only).** `vg playtest run` lets a model play a game. The loop runs _inside the game's page_ (`apps/cli/src/lib/playtest/agent.ts`, injected as source): several times a second it reads `__GAME_DIAGNOSTICS__`, POSTs to `/api/playtest/decide` and holds the answer as real input, with an optional per-frame `reflex` from the game's `window.__GAME_PLAYTEST__` manifest for fast games. Every decision also asks a `score` question — the model's own 0–1 read of progress towards the goal — which the report carries as `decisions.progress`; it is advisory, never a gate. That endpoint is cross-origin and cookie-blind by design — the page is untrusted user code — and honours only a 15-minute HMAC token minted by `playtest.session` for that run (`packages/service/src/playtest/session-token.ts`, signed with `BETTER_AUTH_SECRET`). The server holds `TYPESAFE_API_KEY` and forwards exactly one System One request shape — state plus typed questions — so neither the token nor the key can be used for anything else. Not metered: a run costs a fraction of a cent, and the per-call caps (64 KB state, 32 questions) bound it. `games/pong` is the reference manifest, reflex included. **The globals are the contract; `@vibedgames/playtest` (`packages/playtest`) only types and publishes them** — a game may set them by hand, and the CLI never depends on the package.
- **Media goes through fal (internal only).** `vg generate` exposes `run`, `models`, `schema`, `upload`, `pricing`, `status`, `docs`. The server holds `FAL_API_KEY`; the CLI proxies through the API. fal is a gateway to OpenAI, Veo, Sora, Kling, Flux, ElevenLabs, Retro Diffusion, etc. — there's no per-provider routing. **End-user-facing surfaces (the `vg generate` CLI help and the skills under `plugins/vibedgames/skills/`) must not name fal as a brand.** To the user this is just a CLI that generates assets; "fal" stays an implementation detail. The one exception is model endpoint IDs: they're passed through verbatim (e.g. `fal-ai/flux/dev`, `bytedance/seedance-2.0/...`), exactly as the upstream API expects — the CLI does no id rewriting. Keep branding out of prose and help text, but never alter an endpoint ID.
- **vibedgames is an OAuth 2.1 authorization server (`@better-auth/mcp`'s `mcp()`, built on `@better-auth/oauth-provider`), for MCP connectors and any app acting for a person.** Issuer `${origin}/api/auth`; two protected resources, `${origin}/mcp` and `${origin}/api` (`packages/service/src/auth/oauth-resources.ts`). Discovery documents are served by the plugin from `auth.handler`, so the root `/.well-known/oauth-authorization-server/api/auth` and `/.well-known/oauth-protected-resource{,/mcp}` routes forward to it. Clients identify themselves with a Client ID Metadata Document (`cimd()`, the MCP 2026-07-28 way: the `client_id` is an HTTPS URL the Worker fetches through `cimd-fetch.ts`, which leaves address filtering to Cloudflare's edge and refuses IP literals, plain HTTP and redirects) or register themselves (RFC 7591, unauthenticated, for clients from before it); a registration whose every redirect is `http://localhost|127.0.0.1|[::1]` and that names no `application_type` is rewritten to `native` before routing (`nativeLoopbackClients` in `auth.ts`), because the provider otherwise defaults it to `web` and refuses the loopback redirects Claude Code and Cursor send. PKCE is required. The person signs in at `/auth/login` (the plugin's signed query rides along; `oauthProviderClient()` re-attaches it to sign-in and consent POSTs, and the credentials form must not navigate while `sig` is in the URL) and approves at `/oauth/consent`. Access tokens are `jwt()`-signed JWTs bound to one resource; `resolveOAuthSession` (`oauth-token.ts`) verifies them against the JWKS read in-process (`auth.api.getJwks`, never an HTTP fetch of ourselves), refuses DPoP-bound (`cnf`) tokens, and synthesizes an `oauth:`-prefixed session, which `rejectApiKey` keeps off session-only procedures exactly like a key. Scopes say what a token may do: one per kind of action (`games:read`, `games:write`, `generate`, `credits:read`, `credits:write`, `playtest`; `@repo/contract/auth/oauth-scopes`) plus OpenID's `profile`. Every `protectedBase` procedure declares its scope with `requiresScope` beside its credential, `requireSession` refuses a token without it (FORBIDDEN, `insufficient_scope`), `root-router.test.ts` holds every procedure to having one, and `/mcp` checks a `tools/call` before dispatch so a missing scope is the HTTP 403 `WWW-Authenticate: Bearer error="insufficient_scope"` challenge a client steps up from (built, like the 401, with the provider's `createResourceServerChallenge`). Session cookies, session tokens and API keys carry no scopes and act in full. People list and disconnect apps in Settings (`connectedApps.list`/`revoke`): revoking deletes the consent and the app's refresh tokens, which the provider's own `delete-consent` leaves alive. `createRpcContext(headers, surface)` picks the audience: `/mcp` passes `"mcp"`, every other API route `"api"`, so a token never crosses surfaces. Tokens cannot be revoked before their hour runs out. The JWT plugin's own `/token` is disabled. The token endpoint has no rate limit and registration a loose one, since every claude.ai user arrives from the same few IPs. The provider seeds its `oauth_resource` rows at auth init, and a failed init would fail every auth call, so `seedFailureContained` (`auth.ts`) logs it and starts auth without it: a database missing the OAuth tables (`jwks`, `oauth_*`) costs OAuth alone, and the seed retries on the first OAuth request. `getServerContext` caches one auth instance per isolate and origin so the seed runs once. `string[]`/`json` plugin fields are `text(..., { mode: "json" })` columns: the relations-v2 drizzle adapter passes arrays through to the driver. Social sign-in (GitHub, Google) is on per provider once its `*_CLIENT_ID`/`*_CLIENT_SECRET` pair is set, optional secrets like Stripe's; `/auth`'s loader reports which are on. The providers' callbacks are registered on production only, so a Preview signs in through it with `oAuthProxy` (`OAUTH_PROXY_URL`), which hands the Preview the profile encrypted with `OAUTH_PROXY_SECRET`: the same value on production and in the preview base config, never `BETTER_AUTH_SECRET`.
- **`/mcp` is the platform as MCP tools, bearer-only (OAuth token or API key).** One tool per `vg` command that reaches the server, named for the command with `_` for spaces (`whoami`, `credits_redeem`, `deploy`, `deployments_delete`, `fork`, …; `vg generate run` is plain `generate`) so the CLI and MCP read the same; only the asset tools have no command. `vg skills` and the `skills` tool read the same bundle, the CLI through `/.well-known/agent-skills`. They live in `apps/web/src/lib/mcp-tools.ts`; `mcp.ts` serves them with `@orpc/mcp`'s `McpRegistrar` on a fresh `McpServer` per request (stateless Streamable HTTP). Most tools are `appRouter`'s own procedures; the `generate_*` family is `vg generate`'s subcommands over `generate.forward`, reached through oRPC's `call()` so the session check, input rules and credit ledger run exactly as for the CLI; the dedicated asset tools (`generate_image`, `generate_video`, `generate_3d`, …) are the same path on the defaults `MEDIA_MODELS` names, which `mcp.test.ts` holds to the model-catalog skill. Each tool and its command call the same procedure, e.g. `generate_upload` and `vg generate upload` both call `generate.upload`. Large bytes never ride a tool call: `generate.upload` returns an `/api/upload` URL the caller PUTs to (forwarded to the storage slot), `fork` an `/api/download` URL, and `deploy.upload`'s `presign` files get `/api/upload` URLs, which publish refuses until R2 holds each at its declared size. The `deploy` tool and `vg deploy` are both `deploy.upload`, and the regular way in is one bundle: `bundle: true` returns a signed URL for a `.tgz` of the build (`tar -czf game.tgz -C dist .`), and publish streams it apart into the staged deployment (`deploy/bundle-extract.ts`: ustar, pax and GNU names; caps per file, count and total) before checking `index.html`. `vg deploy` packs the bundle (and `--source`'s `sourceArchive`), PUTs it and publishes in a second call; `presign` (per-file signed URLs) and inline `files` remain for partial updates and shell-less agents. Bundles wait at `bundles/{gameId}/{deploymentId}.tgz`, outside `games/`, and are deleted once unpacked or with their game; `deploy.create`/`deploy.finalize` stay only for CLI installs from before it, and go once those are gone. `deploy.upload` writes inline files through the R2 binding into a staged deployment beside the live one and, on `publish`, points the game at it before removing every other deployment of the game: unlike `deploy.create`, nothing goes dark mid-upload. A `url` file is fetched by the Worker only from the media hosts `isMediaUrl` (`@repo/contract/generate/media-hosts`, shared with the CLI's downloads) names, so it is no general fetch proxy; `source: true` tars the published files in the Worker (`source-archive.ts`) into the same `sources/` archive `vg deploy --source` uploads, so an uploaded game forks like any other. The `mcp.tool` meta lives in `apps/web`, never in `@repo/contract`: the CLI bundles the contract and `@orpc/mcp` would drag the MCP SDK in. The cookie is dropped before the context is built, so only an OAuth access token for `/mcp`, a `vg_…` key or a session bearer signs a call: a game page is same-site with the apex, and SameSite=Lax would otherwise carry the session into a tool call. A request with none answers HTTP 401 with `WWW-Authenticate: Bearer resource_metadata=…/.well-known/oauth-protected-resource/mcp, scope=…`, which is how a connector starts OAuth; `initialize` and `tools/list` need a credential too. POST is the only method (405 otherwise): the server is stateless, so there is no stream to open with GET or session to end with DELETE. Not tools: what only touches the caller's machine (`init`, `login`, `new`, `update`, …) and `playtest run`, which drives a local browser. The skills are also served under MCP's Skills extension (SEP-2640, `io.modelcontextprotocol/skills`, `mcp-skills.ts`): every file of every skill is a `skill://<name>/<path>` resource, and `skills/list`/`skills/get` give each skill's frontmatter and every file's digest and size; the `skills` tool stays for clients without the extension. `mcp.test.ts` holds the tool list, the annotations, the skills extension, the cookie drop and that no prose names fal.

### Contract-first API

`@repo/contract` is the single source of truth: every feature has `<f>-contract.ts` (OpenAPI meta and outputs, built on `publicBase` / `protectedBase` / `sessionOnlyBase` / `adminBase` from `base.ts`), registered in `src/index.ts`, and a feature that takes input keeps it in `<f>-schema.ts` (zod inputs, plus the wire constants clients share; one the browser needs without the schemas, like `INVITE_CODE_LENGTH`, sits in a zod-free file beside it, `auth/auth-limits.ts` or `credits/credits-limits.ts`). `@repo/service` implements it with `os = implement(contract)` — protected: `const authed = os.<f>.use(requireSession); export const <f>Router = { <proc>: authed.<proc>.handler(...) }`; `sessionOnlyBase` adds `.use(rejectApiKey)`, `adminBase` `.use(rejectApiKey).use(requireAdmin)`; public procedures implement `os.<f>.<proc>` directly (see `waitlist-router.ts`). Mount in `root-router.ts`; `os.router` fails to compile if a procedure is missing or mistyped. All three middlewares go on the implementer, which runs them before input validation (anonymous → UNAUTHORIZED, an API key on a session-only procedure → FORBIDDEN); `.use` on a procedure runs after it. Feature routers stay plain objects — `os.<f>.router()` re-applies implementer middleware, so it would run twice. Nothing ties a base to its middleware at compile time: the base declares the credential (in the OpenAPI security, and as the meta `getRequiredCredential` reads, which also names the admin role the document cannot), the router enforces it, and `root-router.test.ts` walks every procedure in `appRouter` and holds it to its base's credential. Clients — `apps/web`'s browser code and the `vg` CLI — type against `ContractClient` / `RouterInputs` / `RouterOutputs` from `@repo/contract`; only server code (route handlers, the SSR branch of `apps/web/src/lib/orpc.tsx`, scripts) imports `@repo/service`. Layout follows oRPC's Hybrid monorepo recipe.

## Environment

One file, two consumers: root `.env` feeds anything reading `process.env` (drizzle-kit, the cf CLI) _and_ the dev Worker's `env` binding, because `apps/web/cloudflare.config.ts` declares each secret with `bindings.secret()` — which makes the dev server fold `process.env` in, filtered to the declared names. A secret not declared there never reaches the Worker. Creating `apps/web/.dev.vars` takes precedence and silently kills the root file; don't. Full table in `AGENTS.md` → Environment.

## Local development & headless verification

Setup, seeded logins and the headless auth recipes live in `AGENTS.md`. What matters architecturally:

The dev Worker (`pnpm dev:web`, http://localhost:5173) binds to a **local** Miniflare D1 — separate from prod, isolated, starts empty. Schema management is `drizzle-kit push` (TS schema is the source of truth, no SQL migration files). Following the fleet convention: `db:push` and `db:studio` target the local D1 via `drizzle.config.local.ts` (which resolves the Miniflare SQLite path); `db:push-remote` is the only command that reaches prod, and the only one that reads `.env.production.local`.

Schema workflow: edit `packages/db/src/drizzle-schema*.ts` → `pnpm db:push` (local) / `pnpm db:push-remote` (prod). No migration files. Re-run `pnpm db:seed-local` anytime (idempotent); re-run `db:push` after schema changes, and restart `dev:web` if a change doesn't show.

**Bytes reach R2 only through the binding.** `signUploadUrl` and `signDownloadUrl` (`packages/service/src/storage/signed-urls.ts`) mint `/api/upload` and `/api/download` URLs on the request's own host, HMAC-signed with `BETTER_AUTH_SECRET`; the routes stream to and from `GAMES_BUCKET`. There are no S3 keys and no direct-to-R2 URLs, so local dev always lands in Miniflare, a Preview in the preview bucket, and a caller (the CLI, an agent's shell) only ever reaches our host. `/api/upload` also forwards a PUT to the one external URL it was signed for — `generate_upload`'s storage slot. A request is capped by the Worker's 100 MB body limit; deploy files are 10 MB each.

## Dogfooding (build games in ./games using local CLI + skills)

`pnpm dogfood` builds + npm-links the local `vg` CLI and syncs `.claude/skills/` to match `plugins/*/skills/*` (creates new relative symlinks, removes stale ones). Symlinks are committed, so a fresh clone gets working skills automatically — only the `npm link` step is per-machine. `pnpm dogfood:reset` undoes the link.

Re-run `pnpm dogfood` after adding or removing a skill, then commit the symlink change in `.claude/skills/`.

### Using a skill outside this repo

Skill docs resolve their scripts through a `SKILL` variable. Under Claude Code it is `${CLAUDE_SKILL_DIR}`, which Claude Code substitutes into the skill body for project, global and plugin (marketplace) installs alike. Other agents leave that literal unset, so the snippet falls back to probing `.agents/skills`, `.claude/skills`, `~/.agents/skills`, `~/.claude/skills` — every location `vg init` writes. In this repo the project probe hits the committed `.claude/skills/` symlinks; the home fallbacks only resolve for a skill you have deliberately linked there — one per skill, per machine, exactly like the `vg` `npm link`:

```bash
ln -s "$PWD/plugins/vibedgames/skills/<name>" ~/.claude/skills/<name>
```

Linked so far: `image-to-threejs`, `generate`. Do **not** bulk-link all 34 — `~/.claude/skills/` is the global namespace shared with `~/.agents/skills`, and a link shadows any same-named skill already there. Scripts still need their own runtime deps in the target project (`image-to-threejs` also wants `three`, `vite` and `playwright` there).

## Claude Code on the web (remote sessions)

A fresh remote clone resolves `.claude/skills/` automatically (the symlinks are committed), but `node_modules` and the `vg` CLI are not present and `vg` is not on PATH. Most sessions only need `pnpm install`; for end-to-end CLI testing (`vg deploy`/`generate`/`whoami`) run `pnpm install && pnpm dogfood` (see Dogfooding above). To reach the backend you also need:

- **Auth:** `VG_TOKEN` set as an environment secret (an API key from Settings: `vg login` needs a person at a browser, and its access token lasts an hour). `VG_API_URL` defaults to prod; override for local/staging. `vg playtest run` needs only these — the decision model's key lives on the server.
- **Network:** egress allowed to `registry.npmjs.org` and the target API host.
